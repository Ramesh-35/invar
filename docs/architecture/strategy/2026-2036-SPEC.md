Report: INVAR 2026-2036: Technical Verification Primitives, Autonomous Agent
Immunity, and Decade-Scale Platform Architecture

## Executive summary

The software industry faces an acute verification crisis driven by the
commoditization of autonomous coding agents and generative model synthesis.
When autonomous agents synthesize thousands of lines of code in seconds,
traditional human review collapses under cognitive overload, transforming
pull request reviews into superficial spot-checks. INVAR must establish
itself as an external, deterministic verification layer that evaluates
explicit software contracts and produces portable, cryptographically bound
evidence receipts [PROPOSED]. It cannot succeed as an internal component of
an AI agent harness, an IDE plugin, or an unanchored linting utility. Its
long-term viability depends on maintaining an adversarial separation between
systems that synthesize code and systems that evaluate whether synthesized
code satisfies declared behavioral and structural properties
[FORMALLY DERIVED].

The irreducible technical core of INVAR consists of four primitives
[PROPOSED]:

1. A deterministic contract expression language and abstract syntax tree
   (AST) evaluator with strict termination guarantees.
2. An append-only, content-addressed lockfile manifest (invar.lock)
   recording canonical AST hashes, authorized waiver cryptographic digests,
   and contract schemas.
3. A five-state normative outcome algebra (HOLDS, VIOLATED, ERROR,
   LOCK_DRIFT, NOT_EVALUATED) mapped directly to deterministic process exit
   codes 0 through 4.
4. An offline-verifiable attestation receipt conforming to the in-toto
   Statement v1.0 specification, enveloped within OpenSSH SSHSIG binary
   formatting, and verified exclusively against external, read-only trust
   anchors.

To maintain epistemic honesty, INVAR must explicitly refuse to make several
classes of claims across its runtime outputs, receipts, and public
specifications [PROPOSED]. It does not claim that a software artifact is
safe, correct, or bug-free; it claims only that named, declared invariants
were evaluated against explicit syntax trees and evaluated to true
[FORMALLY DERIVED]. It does not claim that a newly initialized or accepted
lockfile baseline represents a valid specification; an accepted baseline
proves only that the current workspace matches its recorded historical
digest [OBSERVED]. It does not claim that an OpenSSH or Ed25519 digital
signature establishes truth or runtime correctness; a signature establishes
only that a specific cryptographic private key authenticated a canonical
byte payload [FORMALLY DERIVED]. It does not claim that local agent hooks
provide tamper-proof enforcement; any agent with file-system write or
process-execution privileges within a workspace can modify, suppress, or
bypass local verification configurations [OBSERVED]. Furthermore, it does
not claim that counterfactual analyses of historical software incidents
guarantee the real-time prevention of distributed production crashes
[REFUTED].

Engineering investments must follow a strict dependency order, prioritizing
Phase 0 (Reality Baseline Reconciliation) and Phase 1 (Trust Semantics
Specification) [PROPOSED]. This requires formalizing the normative result
algebra, auditing the actual repository capabilities, enforcing
deterministic parsing and canonicalization, and establishing fail-closed
exit-code contracts before developing distributed agent hooks, IDE
extensions, or web platform interfaces. The project must reject the
immediate development of interactive web-based lockfile visualizers, SaaS
dashboard platforms, native plugins for commercial AI developer IDEs,
autonomous remediation bots that automatically rewrite failing code, and
proprietary consensus ledgers or custom cryptographic envelopes [PROPOSED].

When large AI platforms introduce integrated contract evaluation and test
generation, competitive durability cannot rely on AST parsing algorithms or
command-line conventions [INFERRED]. Defensibility resides in structural
vendor neutrality: operating as an independent auditor that evaluates
outputs across heterogeneous foundation models, autonomous agents, and
compilers without shared corporate incentives [EMPIRICALLY SUPPORTED]. It
also stems from asymmetric verifiability, producing lightweight, portable
receipts that downstream consumers, regulators, and continuous integration
(CI) systems can verify offline, without AI inference compute, at a cost
small enough to run on every change [FORMALLY DERIVED for the offline and
no-inference properties; latency is measured per release, never promised]. Finally, it depends on embedded
organizational policy anchors that maintain public-key signing topologies
and branch-protection controls administered outside the workspace
accessible to code-generating agents [OBSERVED].

The proposed architecture and commercial hypothesis must be abandoned or
radically scoped down if empirical usability trials demonstrate that
software engineers accept modified invar.lock baselines without inspecting
underlying AST contract diffs at a rate exceeding 25%, indicating that
lockfiles have degenerated into uninspected automation noise [HYPOTHESIS].
Similarly, if standard multi-tenant CI pipelines refuse to support non-zero
exit codes (3 and 4) as distinct branch-protection gates, collapsing the
five-state algebra into binary pass/fail, or if major foundation model
providers achieve provably verified zero-shot syntax-and-semantic
correctness directly within compiler front-ends, the fundamental market
need for external verification layers will cease to exist [REFUTED].

## Actual implementation baseline

An empirical audit of the existing codebase (anomly-labs/invar) reveals a
fundamental divergence between the founder's aspirational software-contract
verification architecture and the currently implemented system [OBSERVED].
The repository at release 1.3.0 and tools version 1.21.3 is not a
software-contract verification engine; it is a local Large Language Model
(LLM) inference provenance and attestation server designed to wrap engines
such as Ollama and llama.cpp [IMPLEMENTED]. Its key implemented value
proposition is generating cryptographic computation receipts (CR-v0.1) that
bind runtime binary digests, model weights, prompt templates, decoding
parameters, and generated output tokens into a sequential hash chain termed
a worldline [IMPLEMENTED].

The repository provides several operational CLI commands: invar serve for
OpenAI-compatible endpoint hosting, invar verify for worldline log
verification and logits spot-checking, invar certify for black-box API
determinism benchmarking, and invar attest for binding confidential
computing hardware evidence such as AMD SEV-SNP, Intel TDX, and TPM 2.0 PCR
banks [IMPLEMENTED]. It includes an independent verification implementation
in Go (go/crverify) that cross-checks receipts without executing Python
[IMPLEMENTED].

However, the software-contract verification system described in the
research mandate, including abstract syntax tree contract checking,
codebase lockfiles (invar.lock), code-level waiver models, five-state exit
algebra, and automated agent lifecycle hooks, is entirely unbuilt
[OBSERVED]. The baseline contract checking status is categorized as
[PROPOSED]. The existing codebase does not contain an AST parser for
general programming languages, does not maintain a project-level lockfile
schema for source code, and relies on binary process exit codes where 0
indicates success and 1 indicates an error or receipt mismatch
[IMPLEMENTED].

Therefore, this research report separates the established capabilities of
the local inference engine from the architectural specification required to
build a code contract verifier. All subsequent modules define the normative
architecture for the code-verification engine, establishing a clean-room
design that avoids confusing the implemented inference-receipt server with
the proposed software-contract verifier.

## Module A: Human-first trust primitives

### Calibrated trust model

Trust in software verification tools is an operational equilibrium between
perceived utility and cognitive friction, rather than a purely rational
calculation of mathematical correctness [EMPIRICALLY SUPPORTED]. Software
engineers operate under severe time constraints, making them susceptible to
automation bias. Under high automation bias, developers exhibit
overreliance, treating green status indicators as blanket warranties of
application correctness and accepting automated pull requests without
reviewing underlying logic changes. Conversely, when a verification system
emits excessive warnings or cryptic failure traces, developers experience
alert fatigue and underreliance, actively seeking mechanisms to bypass,
disable, or suppress the verification tool.

Human reliance on foundational developer tooling such as Git, compilers,
and static analyzers is governed by three operational mechanisms
[EMPIRICALLY SUPPORTED]. First, deterministic repeatability requires that
identical repository states evaluated across different environments,
machines, and execution cycles produce bit-for-bit identical verdicts. Any
perception of stochastic behavior destroys developer trust. Second,
transparent negative space mandates that the tool explicitly communicate
what it did not evaluate. Masking skipped files or unsupported language
constructs behind a generic pass indicator creates unjustified confidence.
Third, developer interaction is bounded by strict psychological latency
budgets. In-editor checks must execute within 200 milliseconds to maintain
cognitive focus, pre-commit hooks must complete within 2.0 seconds, and CI
checks must finish within 30.0 seconds. Verification engines exceeding
these thresholds inevitably trigger workflow circumvention.

### Normative outcome semantics and result algebra

Compressing verification outcomes into a binary pass/fail status introduces
catastrophic epistemic flaws [FORMALLY DERIVED]. In binary regimes, an
evaluator encountering an unsupported language feature, an unresolvable
macro, or an execution timeout must either fail the entire build
(triggering developer hostility) or ignore the construct and exit with zero
(silently passing unverified code into production).

The report proposes a normative result algebra over five mutually exclusive
base states, S = { HOLDS, VIOLATED, LOCK_DRIFT, NOT_EVALUATED, ERROR },
with a lattice ordering that enforces strict fail-closed precedence:

ERROR > VIOLATED > LOCK_DRIFT > NOT_EVALUATED > HOLDS

and an aggregate evaluation function that returns the highest-precedence
state present across contract-level outcomes, LOCK_DRIFT additionally
triggered by a workspace digest differing from the lockfile digest, and
HOLDS only when every contract evaluates to HOLDS.

| Outcome state | Exit code | Formal semantics | CI gate action | Cache permitted |
|---|---|---|---|---|
| HOLDS | 0 | All targeted contracts evaluated and satisfied. Zero unsupported constructs in scope. Zero baseline drift. | Allow merge. Pipeline proceeds. | Yes (keyed on AST and policy digest). |
| VIOLATED | 1 | One or more declared contracts disproved by verified counterexample. | Block merge. Regression detected. | Yes (keyed on AST and policy digest). |
| ERROR | 2 | Verifier crash, parser panic, I/O failure, unparseable syntax, or memory exhaustion. | Fail pipeline. Infrastructure error. | No (execution incomplete). |
| LOCK_DRIFT | 3 | Workspace modified without updating lockfile, or unauthorized AST hash detected. | Block merge. Policy mismatch requiring re-authorization. | No (state inconsistent). |
| NOT_EVALUATED | 4 | Contract skipped due to unsupported constructs, inline assembly, or timeout. | Configurable: block on release branches, warn on feature branches. | Yes (keyed on AST and engine version). |

[TRANSCRIPTION NOTE: this exit-code map conflicts with the shipped frozen
map; see 2026-2036-CONFLICTS.md point 2.]

Exit codes 3 and 4 prevent autonomous agents from masking skipped
evaluations behind successful process terminations [OBSERVED]. Shell
scripts, container runners, and CI branch-protection rules evaluate exit
status directly, preventing ambiguous outcomes from reaching production
environments.

### CLI interface and machine-readable schema

Terminal presentation must eliminate ambiguous terminology. The
command-line interface never emits generic claims of total application
safety. Terminal output is structured into four explicit sections: Primary
Verdict, Evaluation Scope, Drift Findings, and Unchecked Property Details.
The report gives a JSON result schema (outcome, exit_code, summary counts,
drift_details with lockfile and workspace BLAKE3 root digests and diverged
modules, unevaluated_items with contract id, target, reason and detail, and
an attestation block with engine version, engine binary digest and UTC
timestamp) and a plain-text tabular report format with sections for
evaluation metrics, drift findings, unchecked property details and
remediation guidance (update the lockfile with authorization, or revert
unauthorized changes).

### Onboarding flow and baseline establishment

A major vulnerability in developer tooling is the unvalidated baseline:
executing an initialization command on legacy or untrusted code, generating
a lockfile, and declaring the system secure. INVAR decouples baseline
capture from trust establishment through a two-phase initialization
ceremony [PROPOSED].

During Phase 1, executing invar init parses the workspace, normalizes
source ASTs, extracts existing contracts, and writes an unsigned
invar.lock.pending file. The command terminates with exit code 4
(NOT_EVALUATED), explicitly notifying the user that the captured snapshot
is an empirical recording of existing state, not a verified specification.

During Phase 2, baseline promotion requires an explicit human signing
ceremony: invar baseline sign --key ~/.ssh/id_ed25519. This operation
embeds the cryptographic signature of an authorized developer into the
lockfile, binding human provenance to the initial snapshot. Standalone
binary distributions (x86_64-unknown-linux-musl, aarch64-apple-darwin,
x86_64-apple-darwin) must be verified via detached OpenSSH signatures
rather than arbitrary curl | sh pipes.

### Habit loop and lockfile semantics

Software lockfiles serve two distinct purposes across engineering
ecosystems [FORMALLY DERIVED]. Dependency resolution lockfiles (such as
Cargo.lock or package-lock.json) record resolved network dependency graphs
to ensure repeatable builds. In contrast, contract lockfiles (invar.lock)
record accepted policy baselines, canonical AST digests, and cryptographic
waivers. Treating invar.lock as an ephemeral build artifact encourages
developers and automated agents to execute update flags blindly
[EMPIRICALLY SUPPORTED]. To ensure durable reviewability, the report
proposes invar.lock as a human-readable TOML manifest with a [manifest]
section (schema version, root AST digest, creation time, minimum verifier
version), an [authorizations] section (baseline signer public key and
fingerprint), [[contracts]] entries (id, scope, AST digest, predicate,
status) and [[waivers]] entries (id, target, rationale, authorizing key,
expiry, SSHSIG signature).

## Module B: Autonomous-system immunity

Immunity against autonomous systems must not be equated with absolute,
impenetrable security. In an adversarial context, immunity denotes the
establishment of deterministic technical boundaries that prevent an
autonomous agent from executing unmonitored, self-authorized mutations of
its verification baseline [FORMALLY DERIVED]. Dimensions: model
independence (no model inference in the verification path), local agent
bypass (authoritative enforcement at remote CI branch protection, since
local hooks are bypassable), waiver manipulation (detached SSHSIG
verification, fail closed), and prompt injection (syntactic isolation;
comments and docstrings stripped at lexing, natural language exerts zero
influence).

Threat model: the autonomous agent has full shell and file-system write
privileges in the local repository. Scenario A, lockfile tampering: locally
unpreventable; remote CI computes the lockfile diff and requires an
out-of-band OpenSSH signature from an authorized key for changes to
contract or waiver blocks, else fails with LOCK_DRIFT. Scenario B, waiver
abuse: waivers must carry an armored SSHSIG over the canonical
concatenation of waiver id, target digest and expiry; the engine rejects
any waiver whose validity window exceeds a maximum duration policy
regardless of signing authority. [TRANSCRIPTION NOTE: the report says 30
days here and 90 days in ADR-003; the shipped cap is 90 days. See
CONFLICTS point 5.] Scenario C, verification suppression: local hooks are
convenience only; true policy enforcement resides in ephemeral CI runners
executing isolated read-only containers governed by organization-level
rulesets. Scenario D, prompt injection via code artifacts: the evaluator is
a deterministic binary over concrete syntax; comments are discarded.

Harness integration: Claude Code lifecycle hooks (synchronous post-tool,
untrusted, halts the agent loop on failure), Cursor project rules
(background lint, untrusted), git pre-commit hooks (semi-trusted), and
remote CI (authoritative, isolated container, hard merge blocks). Reference
configurations are given for a Claude Code post-tool hook running
`invar check --format=json --bail` with a 3-second timeout, and a GitHub
Actions job running a pinned enforcement container, evaluating contracts
against invar.lock with an allowed-signers file, and archiving the receipt
artifact.

Signed evidence receipts: formatted as in-toto Statement v1.0 payloads with
subjects binding the git commit and workspace BLAKE3 digests and the
invar.lock digest, a predicate recording the verifier id, version and
binary digest, the outcome and exit code, evaluated and unevaluated
properties, active waivers, and execution metadata. Field rules: _type and
subject digests REQUIRED; verifier binary digest REQUIRED; outcome
REQUIRED; unevaluatedProperties REQUIRED; sourceCodeText PROHIBITED;
developer identity email RESTRICTED by default.

Offline cryptographic verification: canonicalize the statement with RFC
8785 JCS; sign the canonical bytes with `ssh-keygen -Y sign -n
invar-receipt`; verify air-gapped with `ssh-keygen -Y verify` against an
allowed_signers file. SSHSIG advantages: ssh-keygen ubiquity, namespace
domain separation, flat-file auditable trust roots.

## Module C: INVAR.dev platform architecture

A dedicated domain is justified only as an entirely static,
content-addressed distribution plane: no dynamic server runtimes, no
databases, no third-party telemetry. Information architecture: a static
index with a verified CLI demonstration and checksums; a signature-pinned
install script; docs; normative versioned specifications and conformance
suites; a security section with the threat model and root allowed_signers;
adjudicated incident dossiers with reproducible counterexamples; hermetic
release artifacts with SHA256SUMS and detached signatures. Interactive
browser-based lockfile editors are rejected: dual-parser architectures
(JS/WASM beside the authoritative Rust engine) create parser differentials
and exploitable blind spots; validation happens only in the authoritative
binary.

Empirical incident corpus (counterfactual analyses, explicitly bounded):
CrowdStrike Falcon Channel File 291 (2024-07-19): sensor 7.11 defined an
IPC template type with 20 input fields; Channel File 291 deployed an
instance reading a 21st field; out-of-bounds read crashed 8.5 million
Windows hosts; the internal content validator assumed 21 inputs. A static
cross-file bounds contract between the sensor's field count and the data
payload is DETECTABLE; graceful kernel fault handling is UNDETECTABLE.
Azure Front Door (2025-10-29): a tenant configuration change bypassed
pipeline validation via a software defect and propagated invalid metadata
globally; edge nodes crashed on a latent reference-counting defect; an
8.5-hour global outage. An empty health-probe array is DETECTABLE by a
static contract on tenant metadata; the latent asynchronous memory defect
is UNDETECTABLE. [TRANSCRIPTION NOTE: the report's inline citation markers
("[cite: 19]" etc.) arrived without an attached source list.]

Release distribution: hermetic container builds with network disabled,
pinned toolchains, SOURCE_DATE_EPOCH and --remap-path-prefix for
bit-identical reproduction, SLSA Build Level 3, checksum manifests signed
by an offline hardware key with the public key mirrored across DNS,
organization trust stores and the static site.

## Module D: Competitive defensibility and economic architecture

Every user-facing component is replicable by a funded vendor within six
months; parsers, lockfile serializers and CLIs are commodity. Durable
defensibility: the vendor-neutral auditor position (a code-generation
platform cannot credibly audit its own outputs), the adjudicated incident
corpus, and regulatory conformance profiles (EU CRA Articles 13/25, NIST
SSDF SP 800-218) binding enterprise compliance to signed receipts.
Standards convergence: in-toto Attestation Framework v1.0, OpenSSH
PROTOCOL.sshsig, no proprietary protocols. Buyers: platform engineering
(agent PR volume overwhelms review), CISOs (regulatory liability needs
machine-readable due-diligence proof), supply-chain owners (vendor updates
verified against consumer invariant suites in staging). Monetization
preserves a permissively licensed core; commercial value sits in the
enterprise management plane: key distribution and rotation, policy
registries mapping regulations to contract suites, receipt aggregation
indexes.

## Module E: Ten-year adversarial futures (2026-2036)

Eight scenarios with early-warning indicators and required postures:
(A) AI code dominance: optimize for machine-readable schemas and headless
CI. (B) Vendor internalization of contract checking: position as the
independent multi-model auditor. (C) Agent API fragmentation: rely on POSIX
conventions, never per-agent SDKs. (D) Regulatory explosion: align receipt
predicates with CRA technical documentation. (E) Direct verifier targeting:
memory safety, fuzzing, sandboxing; a parser CVE is systemic. (F) Shift to
centralized control planes: support remote policy anchored to external
signatures. (G) Independent implementations: publish conformance suites;
become the reference standard. (H) Market adoption failure: blanket
waivers and ignored lockfiles refute the premise; scope down. Low-regret
investments: standard envelopes (SSHSIG, in-toto), a deterministic
dependency-light core, the five-state algebra everywhere. High-risk
commitments to avoid: proprietary SaaS receipt databases, coupling contract
syntax to specific runtimes, neural heuristics in the verification path.

## Module H: Domain literature analysis

Automation-bias literature: high perceived reliability shifts humans from
active verification to passive monitoring; compliance with static-analysis
warnings drops sharply when false-positive rates exceed 15-20% or messages
lack localized remediation. Contract-based design: preconditions,
postconditions and invariants give rigorous boundaries, but adoption
falters at whole-program verification; bounded syntactic invariants keep
termination sub-second. Supply-chain security: SLSA and in-toto establish
that assertions about development steps must be decoupled from transport
and cryptographically bound to artifact digests; EU CRA (Regulation EU
2024/2847) mandates verifiable technical files for software distributed in
European markets.

## Final strategic test (verbatim kill criteria)

Abandon or pivot if: engineers accept modified invar.lock files without
reviewing diffs at a rate exceeding 25%; CI platforms refuse distinct
non-zero exit codes as branch-protection gates; foundation models achieve
provably verified correctness inside compiler front-ends; enterprise pilots
bypass verification via blanket wildcards (>60% churn in design-partner
pilots). Decade-scale objective: a single memory-safe static binary that
verifies declared invariants, enforces a five-state outcome algebra, tracks
policy in an append-only manifest, and emits SSH-signed receipts verifiable
entirely offline, assuming nothing about the future path of AI.
