# M1 — The Law of Adaptive Rivalry

> INVAR earns its category only by out-detecting a rival that has been made as
> strong as we can fairly make it.

## Statement

The composite baseline (Semgrep + OPA + OpenTelemetry + Property Testing) is
treated as an **adaptive rival**, not a strawman. Whenever the composite could
plausibly catch a corpus case, the rival is strengthened — better rules, the
correct leg, a fair target — *before* any residue is claimed. A residue claim is
only meaningful against the strongest fair form of the opponent.

## Consequences (Phase 1)

- `[PROVEN]` A case is `PROVEN_RESIDUE` only when every **required** leg
  actually executed. A missing leg is `UNKNOWN`, not a cheap win.
- `[PROVEN]` Local control cases (TC-005) exist specifically to confirm the
  rival is real: if the composite cannot catch cleartext secret logging, the
  rival is too weak and every residue claim is suspect.
- `[HYPOTHESIS]` For each residue candidate, there is no fair strengthening of
  the composite that would catch it. This must be re-tested whenever the rival
  ruleset improves.

## Adaptive obligation

The rival is never frozen. When Semgrep, OPA, or a property runner gains a
capability that could catch a standing residue candidate, that candidate must be
**re-evaluated** against the stronger rival. A residue that survives a weak rival
but not a strong one was never residue.

`[UNVERIFIED]` Any statement that INVAR "beats" existing tooling in general.
M1 constrains such claims to specific, fully-exercised, reproducible cases.
